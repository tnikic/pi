# pi Infrastructure

This repository contains the [pi coding agent](https://github.com/earendil-works/pi-coding-agent) configuration, extensions, and skills for a fully self-hosted AI-assisted development environment.

## How it works

```
~/.pi/
├── config.json              ← Single source of truth for all configuration
├── setup.sh                 ← One-command setup: dependencies, SearXNG container
├── agent/
│   ├── extensions/
│   │   ├── shared/config.ts    ← Reads & validates config.json at runtime
│   │   ├── web-search/         ← Web search via self-hosted SearXNG
│   │   ├── web-fetch/          ← Web page fetching via Playwright/Chromium
│   │   └── issue-tracker/      ← Issue tracking across GitHub, GitLab, Forgejo, and local
│   └── skills/              ← Agent skills (engineering & productivity)
├── containers/searxng/
│   └── settings.yml         ← Generated by setup.sh (SearXNG runtime config)
├── package.json             ← Shared npm dependencies (Playwright, Turndown)
└── node_modules/
```

### The config flow

1. **`config.json`** is committed in the repository — it defines the SearXNG port and a dev-only secret key. This is the single source of truth. No other file hardcodes defaults.

2. **`setup.sh`** reads `config.json`, generates `containers/searxng/settings.yml` from it, and starts a Podman container running [SearXNG](https://docs.searxng.org/) bound to `127.0.0.1`. If `config.json` is missing, setup refuses to run.

3. **At runtime**, the `shared/config.ts` module reads `config.json` and provides the port and secret key to extensions. If the config is missing or invalid, it throws a descriptive error telling you to run `setup.sh`.

4. **Port changes**: if you edit the port in `config.json`, you must re-run `setup.sh` for the container to bind to the new port.

### Quick start

```bash
# Clone and set up
git clone <this-repo> ~/.pi
cd ~/.pi
./setup.sh

# Verify
podman logs pi-searxng
curl http://localhost:59999/healthz
```

## Extensions

Extensions register tools that the AI agent can invoke during a session.

### `web_search`

Search the web using a self-hosted SearXNG metasearch engine. Results are aggregated from multiple engines (Google, Bing, DuckDuckGo, etc.). Supports category filtering (general, news, images, academic, videos) and time range filtering (day, week, month, year).

Powered by a [SearXNG](https://docs.searxng.org/) container managed by `setup.sh`.

### `web_fetch`

Fetch and render a web page using a real Chromium browser via [Playwright](https://playwright.dev/). The page is rendered with JavaScript execution and converted to Markdown for readability. Returns page title, meta description, and word count as metadata.

Uses [Turndown](https://github.com/mixmark-io/turndown) for HTML-to-Markdown conversion.

### `issue_tracker`

Create, list, update, and comment on issues — plus manage labels — across GitHub, GitLab, Forgejo, or a local markdown-based tracker. The backend is auto-detected from `git remote -v origin`. Nine tools: `create_issue`, `list_issues`, `get_issue`, `update_issue`, `comment_issue`, `list_labels`, `create_label`, `update_label`, `delete_label`.

- **GitHub**: Uses the REST API with raw `fetch`. Supports native sub-issues (via GraphQL) and scoped labels (`:` separator). `blocked_by` is read-only (GitHub's dependency API requires node IDs not available via REST). Auth token is collected lazily on first use via an interactive prompt and stored in `~/.pi/agent/issue-tracker-auth.json`.
- **GitLab**: Uses the REST API with raw `fetch`. Supports self-hosted instances (auto-detected via API probe) and `gitlab.com`. Scoped labels use `::` separator (e.g., `priority::low`). `blocked_by` backed by native issue links (full read/write). Sub-issues fall back to a body convention. Auth tokens are stored per-host.
- **Forgejo/Gitea**: Same API surface via raw `fetch`. Scoped labels use `/` separator (e.g., `priority/low`). `blocked_by` is read-only (Forgejo doesn't expose issue dependencies as a writable field). Sub-issues fall back to a task list in the parent body.
- **Local**: Issues live as YAML front-matter markdown files under `docs/issues/`. Labels are tracked in a `labels.md` table. No auth needed — prompts for a username on first use. Full `blocked_by` read/write.

Labels auto-create when applied to an issue if they don't already exist. The `exclusive` flag on labels is honoured by Forgejo and the local backend; GitHub and GitLab ignore it. Uses [typebox](https://github.com/sinclairzx81/typebox) for runtime parameter validation (no other external service dependencies).

## Skills

Skills provide specialized instructions that guide the agent's behavior for specific tasks.

### Engineering

| Skill | Description |
|-------|-------------|
| **bootstrap** | Verify the issue tracker is reachable and set up domain doc layout |
| **codebase-design** | Shared vocabulary for designing deep modules — interfaces, seams, testability |
| **code-review** | Review changes since a fixed point along Standards and Spec axes |
| **diagnosing-bugs** | Diagnosis loop for hard bugs and performance regressions |
| **domain-modeling** | Build and sharpen a project's domain model — ubiquitous language, ADRs |
| **grill-with-docs** | Interview relentlessly to sharpen a plan or design, creating ADRs and glossary as we go |
| **implement** | Implement work based on a spec or set of tickets |
| **improve-codebase-architecture** | Scan a codebase for deepening opportunities, present as an interactive HTML report |
| **prototype** | Build a throwaway prototype to answer a design question |
| **research** | Investigate a question against high-trust primary sources, capture findings in Markdown |
| **resolving-merge-conflicts** | Resolve in-progress git merge/rebase conflicts |
| **tdd** | Test-driven development — red-green-refactor loop |
| **to-spec** | Synthesize the current conversation into a spec and publish to the issue tracker |
| **to-tickets** | Break a plan, spec, or conversation into tracer-bullet tickets with blocking edges |
| **triage** | Move issues through a state machine of triage roles — categorize, verify, write briefs |
| **wayfinder** | Plan large work across multiple agent sessions as a map of decision tickets |

### Productivity

| Skill | Description |
|-------|-------------|
| **grilling** | Grill the user relentlessly about a plan, decision, or idea to stress-test their thinking |
| **handoff** | Compact the current conversation into a handoff document for another agent |
| **teach** | Teach the user a new skill or concept within this workspace |
| **writing-great-skills** | Reference for writing and editing skills — vocabulary and principles that make a skill predictable |
